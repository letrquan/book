# Feature reference

Everything Book does, in one list. The [README](../../README.md) is the short tour, and the other
[guides](README.md) go into each area in depth.

## Features

- **Interactive TUI** (Ink/React) plus **print mode** (`-p`) with `text` / `json` / `stream-json` output for CI.
- **Providers**: Anthropic Messages API (prompt caching, adaptive thinking) and any OpenAI-compatible endpoint, auto-detected from `baseUrl` / `--provider`. `--effort` reaches both, as `output_config.effort` and as `reasoning_effort`, except a model whose `provider.<id>.models.<model>` entry says `effort: false`, which gets no effort on either path. On the OpenAI-compatible path Book sends no cache markers but reads the cached-token counts providers report (`prompt_tokens_details.cached_tokens` and the DeepSeek, Moonshot, OpenRouter, LiteLLM, DashScope and 9router variants) into `/cost`, `/usage` and the USD budget, which prices a cache token with no listed rate at an upper bound (the input rate for a read, twice it for a write).
- **Project context**: walks the tree to load Codex-style `AGENTS.md` and Claude-style `CLAUDE.md` instructions (user-global → broad project → specific project → local/rules; a file reached twice, such as `~/.claude/CLAUDE.md` for a workspace under your home directory, loads once, at its first place; the exception is `CLAUDE.local.md`, which always loads at the local position, after every project file, even when a project file such as `CLAUDE.md` links to it, so a repository's own `.claude/CLAUDE.md` cannot override it; a project, local or rule file found at or below the git repository root (the nearest directory with a `.git` entry; a linked worktree is its own root) loads only if its real path stays inside that root, so a committed `CLAUDE.md` linked to `~/.ssh/id_rsa` is not sent to the provider, and its target must also be a Markdown (`.md`) file, so a link to `.env` or `.book/settings.local.json` inside the repository is skipped as well, while a link to another file in the repository, such as a monorepo package's `CLAUDE.md -> ../shared/AGENTS.md` or `.claude/CLAUDE.md -> ../AGENTS.md`, keeps working; files in your home directory and the directories above it are not checked when they are above the repository root, since those directories are yours (a home-manager `~/AGENTS.md` linked into the Nix store loads); any other directory above the repository root, such as an unpacked archive around a nested `.git`, is checked against itself, and the outer repository of a submodule, or of a worktree inside its main checkout, is checked against its own root; the repository is found from the real path, as git does, so a workspace opened through a link is measured from the repository it is really in; with no git repository a file is checked against the directory it was found in, and a `.git` in your home directory itself (a dotfiles repository) does not count as one, so a project under your home without its own `.git` is checked as one with no repository; your own user-level files are never checked, and a skipped file is reported with a start-up warning; `REVIEW.md` and project `.book/commands/*.md` files follow the same rule; on Windows, a path that is, or reaches through a link, a network (UNC) path such as `\\host\share` is refused by every one of these checks before anything resolves it, so a committed link cannot make Book contact that host (a workspace opened by its UNC path, rather than through a mapped drive letter, therefore loads no project files and inlines no mentions); the `@` file picker leaves such a link out of its list without following it, and offers nothing in a workspace opened by its UNC path; project subagents (`.book/agents`), a project `.mcp.json`, a legacy `.bookrc.json`, `.gitignore` and `.book/rewindignore` on such a path are skipped as well, a linked `.mcp.json` with a warning; an `@path` mention follows the Read tool's boundary instead: it is inlined only when its real path is inside the workspace or an `additionalDirectories` entry (with no Markdown requirement), so a mention of a committed link to a file outside them, such as a monorepo package's link to `../shared/x` when `../shared` is not declared, stays as written, like a mention of `@../x`, and a file left as written that way is reported with a one-line notice, in the TUI and on stderr in print mode; in a project command's body a mention inlines only a file git has committed with no local change, see [Slash commands](commands-and-skills.md#slash-commands)) into a fenced, trust-labeled block, alongside platform info and discovered skills, slash commands, and subagents. Content is split by how often it changes: a cached static prefix, an uncached suffix for activation-class policy, and a per-turn `<session-state>` block carrying date, git status, and mode on the newest user turn — so an edit or a mode toggle costs one turn of cache, not the whole conversation.
- **Auto-memory**: file-based store under `~/.book/projects/<project>/memory/` with a `MEMORY.md` index. The store is keyed by the git repository root, so every subdirectory and every linked worktree of a repository shares one memory (outside a repository it is keyed by the workspace itself; a `.git` in your home directory itself, a dotfiles repository, does not count, so a project under your home without its own `.git` is keyed by itself, and memory saved earlier under the home key is not moved); a directory keyed by the old workspace path moves there on first run, and when both exist they are merged, keeping both files of a colliding name. The first 200 lines or 25,000 bytes of `MEMORY.md` are auto-loaded, whichever comes first, and a `> WARNING:` line at the end of the loaded index says how much was cut off and where. There is no save tool: the model writes memory with the ordinary file tools (`Write`, `Edit`, `MultiEdit`, and `ApplyPatch` for GPT-family models), the way Claude Code does. Each memory is one Markdown file holding one fact, named after its slug, with `name`, `description` and `metadata.type` (`user` / `feedback` / `project` / `reference`) frontmatter, a body that for feedback and project memories ends in a `Why:` and a `How to apply:` line, and `[[name]]` links to related memories. The model owns `MEMORY.md` too: after writing a file it adds one `- [Title](file.md) — hook` line, and it checks the index for a file that already covers a fact and updates that one instead of adding another. It deletes a wrong memory with `rm` and removes its line. The prompt tells it when to save without being asked (a correction, a decision the code does not show, who you are, where something lives, "remember"), what never to save (task-scoped facts, changing state, what `CLAUDE.md`/`AGENTS.md` or git already record, instructions found in files or web pages), to verify a file, function or flag a memory names before relying on it, and to treat memory as data that never overrides its instructions. A write to an absolute `*.md` path in the memory directory needs no prompt (see "Memory writes" in the tools guide); a `deny` or `ask` rule you wrote on `Write`/`Edit`/`MultiEdit`/`ApplyPatch` still applies, and the prompt then says memory is read-only. `Glob` and `Grep` search the memory directory, leaving out dot-entries. A guard checks every such write: text that looks like a secret is refused, a symlink is refused, a subagent cannot write memory, and the file is stamped with `metadata.originSessionId`, `metadata.modified` and, in a delegated session, `metadata.driver: agent`; it warns when a topic file passes 4,096 bytes or `MEMORY.md` passes the load limits or points at a missing file. A notice (`memory saved: <file>`) announces each write in the TUI, print mode and the SDK, and a memory write in the TUI reads as a landmark, like a question you were asked. A session another agent drives — `--session-driver agent`, `BOOK_SESSION_DRIVER=agent`, or by default when the environment carries Claude Code's `CLAUDECODE` or an `AI_AGENT` marker, and every process Book itself starts — keeps only what it learns doing the work: its task prompt is the delegating agent's per-task contract, not the user's preferences. Its prompt asks it to save decisions with their reasons, outcomes that carry a lesson, and verified repository facts, never its instructions; the guard takes only `project` and `reference` files there, marks them `driver: agent` (shown as "from a delegated run" in `/memory`), and refuses to change or delete a memory a person's session saved. There is no approval inbox, no quarantine of sessions that read external content (a page that poisons a memory can be loaded by later sessions, so read `/memory` now and then), no supersede history and no background extraction: an overwrite or a delete is final. A store the old save tool wrote is migrated once, the first time a session loads its directory: the whole directory (dot-entries included, symlinks skipped) is copied to `memory.legacy-<YYYYMMDD>/` beside `memory/` (`-2`, `-3`, … when that name exists) before anything changes, and if the copy fails nothing is touched and the next session tries again. Each approved file is then rewritten in place as `<slug>.md` (a kebab-case slug of its title, at most 60 characters) with `name`, a one-line `description` (its old index hook, else its first body line) and `metadata` holding `type`, `originSessionId`, `modified`, `evidence` and, for a delegated run's file, `driver: agent`; the old `# Title` heading and every other legacy key are dropped. Superseded, pending and discarded files, the `.inbox/`, and the extraction state and lock files are not carried over and survive only in the backup. `MEMORY.md` is rewritten as `- [Title](slug.md) — description` lines (at most 150 characters each) after the hand-written lines it already held, and a `.format` file marks the directory as migrated. `/memory status` and `book doctor` name the backup while it exists. `/memory` shows each memory from its frontmatter (a file the old layout wrote, with a top-level `type`, reads the same, as does one left behind by a migration that could not run; one the old save tool retired with `status: superseded` is listed as legacy), the index lines and bytes against both limits, and says when the index was cut; `book doctor` reports the same numbers. `/memory delete <file>` removes a file and every `MEMORY.md` line linking to it. `memory.autoSave: false` makes memory read-only. To tidy the store, run `/memory consolidate [focus]`: one agent pass in the current session (it also runs headlessly with `book -p "/memory consolidate"`) that merges near-duplicate files, rewrites or deletes memories the code or a newer memory contradicts, makes relative dates absolute, prunes `MEMORY.md` to valid one-line pointers under its limits, and reconciles feedback and project memories with `CLAUDE.md` / `AGENTS.md` without ever editing them (a memory that is clearly newer is annotated `Contradicts CLAUDE.md — verify which is current.` and listed in its summary). It can only write `*.md` files in the memory directory and `rm` them, and it is refused in plan mode, with memory off or read-only, or with no memory files yet. There is no automatic consolidation.
- **Sessions**: append-only JSONL persistence with automatic titles from the first prompt plus `--resume`, `--continue`, `--session-id`, `--name`, and `--fork-session`; in-TUI `/clear` / `/new` / `/reset`, `/resume`, reference-aware `/compact`, and Claude-style `/rewind` for conversation, code, or both. Compaction reduces provider context without deleting the scrollable transcript: old re-derivable tool outputs are masked first, recent messages stay exact, your own earlier turns are kept verbatim ahead of the checkpoint instead of being paraphrased, only assistant and tool activity is summarized -- into a Markdown handoff with a host-built list of the files touched -- and older evidence remains addressable by stable session references (see "Compaction" in the long-runs guide).
- **Live sessions registry**: while the interactive TUI runs, it keeps a record of itself in `<BOOK_HOME>/live-sessions/` (`~/.book/live-sessions/` by default, a `0700` directory of `0600` files), named `<pid>.<domain tag>.json` so containers sharing a home never collide (plain `<pid>.json` on Windows): its pid and process start time, session id, workspace, Book version, a name such as `book-3f` (the workspace's directory name plus two random hex digits, re-rolled if a live session holds it, or `BOOK_SESSION_NAME`), and whether it is `busy` (a turn, a send being prepared, or a compaction), `waiting` (on a permission prompt, or for input) or `idle`. Inside a git repository it also names its worktree, repository and branch, and its last 20 edited paths (see Peer awareness). It is rewritten when that changes and refreshed about every ten minutes, and goes when the TUI exits. The next read of the registry sweeps a record whose process is gone (or whose pid now belongs to another process), a record from another pid domain that has not been refreshed for a day, and a crashed write's leftovers. Print mode, the SDK and agents never register. `book doctor` shows how many sessions are live.
- **Cross-session messaging (experimental, #620)**: the live-sessions registry is the address book. With `messaging.enabled` on (read only from `~/.book/settings.json` or `--settings`; see [Configuration](configuration.md#cross-session-messaging-experimental)), the interactive TUI opens an inbox — a `0600` socket in a vetted `0700` directory, plus a `0600` key file beside its record holding the token every connection must open with — and its record gains `messagingSocketPath` and `features: ["inbox"]`. The model then has two core tools: `SessionList` lists the other live sessions on the machine as `name [ref] · kind · status · started`, its own name first, and `SessionSend` sends one of them a message by name (`name [ref]` when two share a name, or a message's `from` address to reply to it); see "Cross-session messaging tools" in the [tools guide](tools-and-safety.md#cross-session-messaging-tools). A message travels in Claude Code's `<cross-session-message>` envelope and frames, and the inbox applies Claude Code's limits (30 messages per sender at once, refilled at one every 2 s; an identical body within 30 s is a duplicate; 50 waiting at most; a relay that passed through the session 10 times, or 28 sessions in all, is a loop). A message sent in a turn another session's message started carries that relay on, and so does one sent in a turn a completion or notice started after it; one sent in a turn the user started starts a new relay, and a session refuses to send on a relay the other side would drop. The receiving TUI delivers it once it is idle, at most 10 messages and 64 KiB a turn (one larger message alone, cut short with a note), as a turn of its own under a "Message from <name> [ref]" row, never under the prompt mark: its model reads the envelope with every harness tag in the body neutralized, then a paragraph saying the message is another session's request, not the user's, to be acted on within the session's own permissions, and never approval or escalation. A message that is not a well-formed envelope is delivered as text with no sender. The sender hears what came of it: a `✓ … was delivered` row in its transcript, or a `⚠` row plus a `[Cross-session delivery notice]` for its model when the message is dropped, held, denied, expired or refused (held: not delivered yet, so do not wait for a reply or resend while it is held). **Idle notices (#620 PR 6).** `SessionSend {to, notify_when_idle: true}` asks that session for one `[Cross-session idle notice]`, with a message or without one (the message goes first, and the subscription only once it went): the notice comes when the session next goes idle — its turn over, with nothing running, asked or queued, for 750 ms, so a subscription to a session that is already idle is answered after those 750 ms — or when it exits, and never twice. While a peer message waits in its queue or is held for its user, the notice waits too, judged again every 30 s. A session keeps 32 subscriptions, at most 4 from one reply address (Book cannot verify a peer's pid, so it counts addresses), takes one only from an address a live session advertises, and evicts the oldest when full; an unfired one expires after 12 hours, and its subscriber hears `expired` (or gives up by itself 5 minutes later, for a session killed outright). The notice carries the start of the session's last reply (280 characters, folded to one line, harness tags neutralized, provider secrets redacted) only to a subscriber its receive policy would accept a message from now; a subscriber from the other permission class learns only that it is idle. The subscriber's user sees each notice as a `◦ Cross-session idle notice` row; its model hears it too, as a turn of its own in the class a message from that session would run in, only when its own receive policy would accept a message from that session, and otherwise never. A session already waiting for a notice from a session does not subscribe to it again: the one notice answers both requests. **Holding (#620 PR 5).** A message from a session in the other permission class — `bypassPermissions` and `auto` on one side, every other mode on the other — is held rather than delivered, and so is one that names no mode when the receiving session runs without asking (a mode no class has is held too). A held message is a `⚠ Held peer message — from <name [ref]> (peer claims name: …); preview: «…» — not delivered (N held)` row, with everything the peer wrote folded to one line, its harness tags neutralized and the preview cut, plus a sheet that asks once per sender, with how many it has held from that sender: deliver the oldest now, deny it, deny everything from that sender (and refuse what it sends from the other class for the rest of the session), deny everything held, or decide later. The sheet opens on Later, ignores keys for half a second after it appears, stops its arrows at the ends, and only the arrow keys and Enter answer it. Later puts the whole sender off, its next messages too, and asks again when the session goes idle after a turn, at most every 5 minutes; the status line shows `held N` while anything is held. An approval that finds the delivery queue full keeps the message held and asks again once there is room. Up to 100 messages are held, the oldest expiring to make room; one unanswered for `messaging.approvalTimeout` (5 minutes) expires, and every message not yet delivered — held, released or queued — expires when the session ends. A permission-mode change (Shift+Tab included) judges each held message again and releases the ones the new mode accepts, and every queued message is judged again when it is delivered and once more when its turn starts, so a later change of mode or of `messaging.inbound` still applies; only your own approval outlasts a stricter mode or `inbound: hold`, never `inbound: refuse`. A delivered peer turn is pinned to its permission class, the stricter of the sender's and this session's, and always the prompting class for a message you approved: switch into `bypassPermissions` or `auto` while it runs and its tool calls keep asking as `default` would, while a stricter mode applies at once. The pin stays on the turns that carry the peer's work on — a background job's or an agent's completion, a delivery notice — until you start a turn yourself, and a background job a pinned turn started keeps it for its own completion even after that. A pinned turn cannot enter or leave plan mode: changing this session's mode is yours to do. A prompting-class one cannot start or steer a managed agent (`AgentSpawn`, `AgentPlan`, `AgentSend`), since an agent outlives the turn; any pinned turn asks before `AgentStop`, `AgentApply` or `AgentSend`, in every mode, since the agent is most likely yours; and a `Task` subagent it starts keeps the turn's class even if it starts from the queue after you switch to bypass. `messaging.inbound` accepts, holds or refuses everything instead (see [Configuration](configuration.md#cross-session-messaging-experimental)). A message waits for the turn in progress to end; it is not read mid-turn yet. An `@`-mention of a live session — `@book-36`, or `@book-36 [ref]` when two sessions share the name — tells the model who you mean: `@` completion offers the other sessions that have an inbox above the files, labelled `[Session]` (up to three for `@` alone), and a mention in a turn you start adds a note to that turn's `<session-state>` block naming `SessionSend` and the session's address, the bare name unless another live session holds it too (so a `SessionSend(book-36)` allow rule covers the send), to be used only if you asked for a message to be sent. A name two sessions with an inbox share gets a note to ask you which one instead, this session's own name a note that it is this session, a session with messaging off a note that it cannot be reached, and a session your permission settings refuse a send to (a deny rule on any of its spellings, or `dontAsk` without an allow rule) a note that they block it. A file or directory of that name keeps the mention a file mention, a mention inside backtick code is not one, and only text you type is read, not where `SessionSend` is unavailable (plan mode, an allowed-tools list without it) or with `toolDiscovery.intentRouting` off. Both read a snapshot of the live sessions that is read again only when a mention needs it and it is more than a few seconds old, so a word like `@types/node` costs nothing. The note sends nothing: a message still goes through `SessionSend` and its permission check. Print mode, the SDK, managed agents and subagents have no inbox and no messaging tools, so nothing is ever held there, and Windows is not supported yet. With the setting off, nothing of this exists.
- **Peer awareness (#620)**: Book tells the model, without being asked, when something else is working on its files, and tells you when two sessions edit the same one. It works with `messaging.enabled` off, because the live-sessions registry is written whenever the TUI runs.
  - **Changed on disk.** Before each turn, every file the model has read or written this session (the 256 most recent, each `stat`ed and read again only when its size or mtime moved) is checked against what the model last saw. A file that changed since, by you, a formatter, or another session, gets a line in that turn's `<session-state>`: "`<file>` changed on disk since you last read it" (or "was deleted or moved"), with the change as a diff when it is 20 lines or fewer, provider keys redacted (a file that became a symbolic link, or sits under a directory that did, is reported without a diff and never read through the link), and a reminder to take it as the current state rather than revert it. At most 10 files a turn are named and any more are counted in one line, so a branch switch is one notice rather than several turns of them; each change is reported once (a turn cancelled before its block is sent reports nothing, and the next turn does), and the model's own edits and deletions never are. This part also runs in print mode and the SDK.
  - **Other sessions in this worktree.** The TUI's record also carries its git worktree, repository and branch, and its last 20 successful edits (`Write`, `Edit`, `MultiEdit`, `ApplyPatch`, `NotebookEdit`): paths relative to the worktree, taken from the tools' results, never file content and never memory files. When live sessions share this worktree, the turn's `<session-state>` names up to three of them, with their status, branch and recent edits (for example `Other Book sessions in this worktree: book-36 (busy, branch feat/x; recorded edits: src/a.ts 2m ago)`), and counts the rest; sessions in other worktrees of the same repository are only counted, and their paths never reach the model. Each read lists the registry, parses up to 256 records of this machine's pid domain (each capped at 64 KiB), keeps the ones in this repository, and checks at most 8 of them for liveness, the most recently written first, so sessions elsewhere on the machine never crowd out a peer here.
  - **Who changed it.** A changed-on-disk line, and the refusal a write gets when the file changed since the model read it, name the live session in this worktree whose recorded edit of that path came after the read: "`book-36` recorded an edit to `src/a.ts` 1m ago. Re-read it; if your changes overlap, coordinate with `SessionSend` to `book-36 [ref]`" when both sessions have messaging, and "tell the user another session is editing it" otherwise. It is hedged because the record is that session's own claim.
  - **Overlap warning.** When this session and a live session in its worktree both recorded an edit to the same path within 10 minutes, the TUI shows a `⚠` row naming the other session and the path, whatever the model does: right after this session's edit, and, while its own edits are recent, within about 15 seconds of the other session's. Each (session, path) pair warns once per 10 minutes, and the row is never saved to the session file.
  - Every name, branch, status and path another session wrote is stripped of control and invisible format characters, capped and has its harness tags neutralized before the model or the screen sees it, and a recorded edit with an absolute or UNC path, a `..` segment or a future date is ignored. Only the root interactive session records edits: a `Task` subagent's or a managed agent's are not recorded. Outside a git repository there are no peer lines, attributions or warnings. `npx tsx scripts/peer-awareness-eval.ts` runs a mock two-session scenario with peer awareness off and on and reports lost edits and conflicts noticed.
- **Tools**: a provider-neutral capability catalog keeps a practical core loaded and uses `ToolSearch` to activate up to five authorized git, web, session, skill, agent, notebook, or MCP definitions on the next model turn. File, shell, task, clarification, and plan tools stay immediately available when permitted. Existing names such as `Read`, `Bash`, and `AgentSpawn` remain stable.
- **Slash commands**: built-ins including `/jobs`, `/agents`, `/agent`, `/init`, `/model`, `/effort`, `/config`, `/permissions`, `/cost`, `/usage`, `/context`, `/memory`, `/diff`, `/export`, `/skills`, `/review`, `/security-review`, `/release-notes`, `/feedback`, `/compact`, `/rewind`, `/clear`, `/resume`, `/goal`, `/advisor`, plus custom commands from `.book/commands/*.md`. Print mode resolves commands through the same registries: `/init`, `/security-review`, `/review`, and custom commands run headlessly, and the interactive-only ones fail loudly instead of reaching the model as text.
- **Permissions**: allow/ask/deny rule matching with six modes — `default`, `acceptEdits` (`accept-edits`), `plan`, `auto`, `dontAsk`, `bypassPermissions` — see `/permissions` or `--permission-mode`. At a tool prompt, `A` arms **Always allow** and presses again to widen the rule it will write (`Bash(npm run check)` → `Bash(npm run *)` → `Bash(npm *)`); the pattern is always shown before Enter commits it. The prompt shows the whole command, wrapped to the terminal, and for `Edit`/`MultiEdit`/`Write`/`ApplyPatch` the diff the call would make, computed against the file on disk before anything is written; `D` opens a cut the card had to make. `/permissions` lists the rules in force and removes the selected one with `x`.
- **Sandbox & hooks**: optional bubblewrap sandbox for Bash; lifecycle hooks (JSON-over-stdio) for `PreToolUse` / `PostToolUse` / session events. Project-declared hooks require one-time approval per workspace, as do providers a repository declares (`book trust provider`); review MCP settings and custom-command substitutions before opening an untrusted workspace.
- **Verified managed agents**: adaptive model-directed routing, purpose-named runs, compact parent-facing results, live TUI monitoring, profile model overrides, read-only non-Git exploration, resumable isolated worktrees, strict capabilities, typed evidence, independent validation, and explicit patch application. Built-in `explorer`, `patcher`, and `validator` profiles can be overridden under `.book/agents/`.
- **MCP**: interoperable MCP tool client with stdio, Streamable HTTP, and legacy SSE transports;
  interactive project-server approval, secret-safe diagnostics, dynamic tool discovery, and
  server-scoped permissions.
- **CLI helpers**: `book doctor` (diagnose env/config), `book config` (get/set/list settings, and `provider-key` to replace a provider's API key), `book trust` (approve or reject configuration a repository declared), `book auth status` (the experimental Sign in with ChatGPT state), and `book tool-stats` (measure tool use across sessions — fail counts, rates, durations). None of them require a working credential — they exist to help when the provider is not yet configured, so `book doctor` reports an unresolved key as a finding rather than failing on it. When a settings layer is what is broken, `book doctor` names the layer the failure first appears with, and `book doctor --no-settings` reports everything else with all of them skipped. Under `Node:`, `book doctor` flags a Node.js that is missing a fix from the newest Node.js security release Book knows, the same notice every launch shows.
